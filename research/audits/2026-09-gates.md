**The common root cause, stated once:** every gate that was wrong computes a statistic on the
strategy's *raw* net return `r_s` and compares it to **zero** (DSR/PSR) or compares a *total* to a
benchmark total with **no uncertainty** (`ret > bh`). The only statistic that measures skill is one
computed on the **active return** `a_t = r_s,t − r_b,t` against a **named benchmark** `b`, with an
error bar. `significance_vs_ew` is the only gate in the codebase that does this today.

**The rule to adopt (one sentence for `CLAUDE.md`):** *A gate may only consume the active-return
series versus a named benchmark; a comparison of two total returns is display, never a gate.*

## 1. `diagnostics.deflated_sharpe_ratio` — WRONG as a skill gate

**What it computes (L97–106).** `sr = net.mean() / sd` is the per-bar Sharpe of the *raw* net
return. `sr0` (L104) is the Sharpe you would expect from the *best of N* trials under the null of
**zero** true Sharpe. The return value is `Φ((sr − sr0)·√(T−1) / denom)` — the probability that
the true raw Sharpe exceeds `sr0`. The Bailey–López de Prado formula is implemented correctly
(expected-max term L63–68, skew/kurtosis denominator L105 both match the paper).

**What "deflated" changes and what it does not.** Deflation moves the threshold from 0 to
`sr0 > 0` to pay for having searched N configs. It does **not** change *what* is being measured:
the input is still `r_s`, so the hypothesis is still "this thing makes money", now "…even after
accounting for having tried N times". A benchmark never enters the formula. With `n_trials=1`
(`sr0 = 0`, the `xsect.py` case) it is exactly the probabilistic Sharpe, P(true Sharpe > 0).

**Can pure beta pass it?** Yes, and it does:

| Series (net of 3/1 bps, daily, 2018-07 → 2026-07) | Sharpe | % bars long | DSR/PSR (N=1) |
|---|---:|---:|---:|
| SPY buy-and-hold | 0.83 | 100 | **0.990 — passes ≥ 0.95** |
| SPY buy-and-hold scored as "best of 12" (grid var from meanrev configs) | 0.83 | 100 | 0.798 |
| SPY random long/flat, seed 1 | 0.03 | 50 | 0.536 |

Holding the index with zero decisions clears the gate. The only reason random long/flat fails is
that flipping a coin every day pays ~2.5 bps of turnover cost per bar and bleeds to −4.7%; a random
strategy with a longer holding period would pass on beta too (the `xsect` random baselines in §4.1
demonstrate exactly that, PSR ≥ 0.996 for all five seeds).

**The concrete fix.** Do not change the function; change its *input*. Add an explicit
benchmark-relative entry point and make every gate call that one:

```python
# diagnostics.py -- proposed additions (spec, not implemented)

def active_returns(strat_df, bench_df):
    """Per-bar ACTIVE return on the shared index: strategy net minus benchmark net.
    Both frames come from run_backtest/run_panel under the SAME cost model.
    Rows where either side is missing are dropped (never filled)."""
    a = strat_df['net'] - bench_df['net'].reindex(strat_df.index)
    return a.dropna()

def config_active_sharpes(px, fn, grid, cost_model, bench_pos, ppy=252):
    """Full-sample annualised Sharpe of (config_i net - benchmark net) for every config --
    the trial distribution the ACTIVE deflated Sharpe needs (replaces config_sharpes)."""
    bench, _ = run_backtest(px, bench_pos, cost_model, ppy)
    out = []
    for params in grid:
        o, _ = run_backtest(px, fn(px, **params), cost_model, ppy)
        a = (o['net'] - bench['net']).dropna()
        sd = a.std(ddof=1)
        out.append(a.mean() / sd * math.sqrt(ppy) if sd > 0 else float('nan'))
    return out

def active_deflated_sharpe(strat_df, bench_df, n_trials, trial_active_sharpes=None, ppy=252):
    """P(the strategy's edge OVER `bench` is real, not best-of-N luck). This is the number a
    gate may consume. deflated_sharpe_ratio(raw) stays available for display only."""
    return deflated_sharpe_ratio(active_returns(strat_df, bench_df).values,
                                 n_trials, trial_active_sharpes, ppy)
```

Semantics that must hold: (i) `bench_df` is produced by the same engine under the same
`CostModel` and on the same index as `strat_df` (for a scan row: the ticker's own buy-and-hold
walk-forward output, `walk_forward(px, factory(buy_and_hold), [{}], ...)`, which `scan_universe`
already computes at L92); (ii) the trial Sharpes passed in are *active* Sharpes, otherwise the
`sr0` threshold is in the wrong units; (iii) NaN when `sd == 0` (a strategy identical to its
benchmark has no active return to test — B&H vs B&H must come out NaN, not 0.5).

`diagnose()` (L180–198) gets a `bench_df=None` parameter; when given, it stores
`deflated_sharpe_active` and the red-flag threshold (L165–168) switches to that key. Keep the raw
`deflated_sharpe` in the dict for the webapp, labelled "vs zero (beta included)".

## 2. `scan.py` — `EDGE?` / `suspect` / `dead` — WRONG

### 2.1 What the bar actually is

L114–122:

```python
beats_bh  = ret > bh                     # point comparison, no error bar
beats_rnd = ret > rnd                    # point comparison vs ONE random seed
beats_spy = spy is None or ret > spy     # point comparison; spy is raw price (L102), bh is net
survives_gate2 = beats_bh and beats_rnd
significant = dsr == dsr and dsr >= 0.95 # gate 1: raw DSR vs ZERO
clean = survives_gate2 and beats_spy and ret > 0 and tpf >= 30 and significant
```

So the only statistic with an error bar (`significant`) is the one that ignores the benchmark, and
the three that name a benchmark have no error bar. The docstring's claim (L19–21) that N "is the
minimum bar plan/11 requires" is met; the claim at L119–120 that `clean` "clears the REAL bar" is
not — a strategy that is long most of the time in a name that went up 10× clears `significant`
with no timing skill at all, and then needs only to nose past `bh` by any margin.

### 2.2 Evidence on the 30-name scan (93 rows)

- **13 of 93 rows are `significant` (raw DSR ≥ 0.95). All 13 are 66–88% long** in names that
  rose 2–38× (NVDA, LLY, AVGO, GOOGL, META, JPM, MSFT, WMT, CAT). Re-scored with the active
  DSR of §1 (benchmark = the ticker's own buy-and-hold through the same folds, active trial
  Sharpes from the same grid): **0 of 93 ≥ 0.95**; the 13 "significant" rows score 0.00–0.40.
- What stopped them from being `EDGE?` was **not** the significance gate. Twelve failed
  `beats_bh` (they made less than holding the stock). The thirteenth, **META/tsmom** (OOS
  +337% vs B&H +212% vs SPY +171%, raw DSR 0.98, active DSR 0.40), cleared *every* return bar
  and was `suspect` only because it traded 12 times per fold, under the 30 floor at L44. Had it
  traded ≥ 30 times, the scan would have printed an `EDGE?` on a 66%-long trend rule whose
  edge over simply holding META is indistinguishable from luck. The thin-trades heuristic is
  doing the job the statistics gate was supposed to do.
- The 0 EDGE? headline in `CLAUDE.md` is therefore true but for the wrong reason, and it would
  not survive a candidate that trades more often.

### 2.3 Multiple testing: the wrong N

L107 sets `n_trials = len(grid)` (9, 12 or 2). L240 then prints: *"none clears the deflated-Sharpe
discount for having searched {len(rows)} configs"* — 93. The discount for 93 is never applied.
Two errors pulling opposite ways:

1. **Over-penalised on the grid axis.** The DSR is applied to the walk-forward OOS series. That
   series has *no* in-sample selection bias — parameters were chosen on train only — so the
   correct best-of-N discount for the grid, on that series, is N = 1. Charging N = 12 on top of
   walk-forward is a category error (conservative, but it means the number is not what the
   docstring says it is).
2. **Un-penalised on the scan axis.** The real selection happens when a human reads the top of
   a table of 93 OOS results. The cross-row sd of OOS Sharpe is 0.41; `E[max z]` for N = 93 is
   2.50; so under the null the best row in the scan is expected to show an annualised Sharpe of
   **≈ 1.0**. That is exactly the magnitude the "top 20" table prints. Nothing discounts it.

### 2.4 The random baseline is not a bar

`BASELINES['random']` is one seed of `random_strategy` (p_long = 0.5, redrawn every bar). It
turns over ~50% per bar and bleeds ~2.5 bps a day; on SPY it returns −4.7% while B&H returns
+210%. Every row in the table above shows `beats_rand = Y`. A bar that everything clears is not a
bar. (`xsect.py` has the same defect with one seed: five seeds of random top-10 return 203%,
277%, 317%, 352%, 391% against momentum's 309% — momentum beats two of five; `plan/12` already
reports "26% of 200 random tries did as well or better".)

### 2.5 The concrete fix

Replace L104–130 of `scan_universe` with this logic (names are prescriptive):

```python
# per ticker, computed ONCE (already at L92 for buy_hold):
bh_comb, _ = walk_forward(px, _factory(buy_and_hold), [{}], cost_model, n_folds=n_folds)
spy_comb = None
if benchmark is not None:                       # SPY through the SAME cost model + folds
    spy_px = benchmark.reindex(px.index).ffill()
    spy_comb, _ = walk_forward(spy_px, _factory(buy_and_hold), [{}], cost_model, n_folds=n_folds)

# per (ticker, strategy):
combined, _ = walk_forward(px, _factory(fn), grid, cost_model, n_folds=n_folds)
ts_act = config_active_sharpes(px, fn, grid, cost_model, buy_and_hold(px))
dsr_vs_bh  = active_deflated_sharpe(combined, bh_comb,  n_trials=1, trial_active_sharpes=None)
dsr_vs_spy = (active_deflated_sharpe(combined, spy_comb, 1) if spy_comb is not None else 1.0)
```

Then, after the loop over all rows (second pass), the scan-level discount:

```python
# the selection that actually happens: reading the best of len(rows) OOS results
act_sharpes = [r['active_sharpe_vs_bh'] for r in rows]          # annualised, one per row
for r in rows:
    r['dsr_scan'] = deflated_sharpe_ratio(r['active_vs_bh'].values, n_trials=len(rows),
                                          trial_sharpes=act_sharpes)
```

New verdict rule (replaces L118–122 and L140–143):

```
significant = dsr_vs_bh >= 0.95 and dsr_vs_spy >= 0.95 and dsr_scan >= 0.95
clean       = significant and ret > 0 and tpf >= MIN_TRADES_PER_FOLD and rand_pct >= 0.95
verdict     = 'EDGE?' if clean
              else 'suspect' if (dsr_vs_bh >= 0.95 or dsr_vs_spy >= 0.95)   # significant on one bar
              else 'dead'
```

where `rand_pct` replaces `beats_rnd`: the percentile of the strategy's OOS *active* return vs
own-B&H among **≥ 200 seeds** of a random strategy with the **same average holding period** as
the candidate (resample `random_strategy` so it redraws every `k` bars, `k = len(combined) /
num_trades`), each run through the same folds and cost model. A single-seed baseline is deleted.
`beats_bh` / `beats_spy` remain as *display* columns only.

Keep `n_trials = len(grid)` printed in the `N` column as plan/11 requires (it documents the
search), but it no longer feeds a gate. Rewrite L240 to name the N actually applied.

Cost: `walk_forward` is ~40 ms; the fix adds one B&H run per ticker, one SPY run per ticker, and
200 random runs per row (≈ 8 s per row at 40 ms, ~12 min for the scan — or reduce to 100 seeds).
$0 either way.

## 3. `diagnostics.red_flags` — one-year-wonder and regime flags — PARTIALLY RIGHT

Both flags ask the right *shape* of question (is the result concentrated in one year / one
regime?) about the wrong *series* (raw return instead of active return).

### 3.1 One-year-wonder (`_best_year_share`, L132–140; flag L169–171)

Share of the strategy's own log return contributed by its best year. For a long-only strategy the
raw return is mostly beta, which is spread across years; the *edge* can be entirely in one year
and the flag stays silent. Panel evidence (momentum vs EW, 30-name core):

| Series | Best year | Share of total log return | Flag (> 60%)? |
|---|---|---:|---|
| Momentum raw return | 2024 | 25% | no |
| **Momentum − EW (active)** | 2024 | **156%** | **yes** |

Active return by year: 2019 −4.4%, 2020 +0.3%, 2021 −5.6%, 2022 +8.9%, 2023 −3.9%, 2024 +10.3%,
2025 −2.8%, 2026 (partial) +4.7%. Without 2024 the seven-year edge is negative. The gate that was
designed to catch exactly this pattern could not see it because it was looking at 309% of mostly
beta.

**Fix.** `per_year_returns(net)` gains a `bench=None` argument and, when given, returns a
`per_year_active` list with `active = (1 + r_s) / (1 + r_b) − 1` per year. `_best_year_share` is
called on the active list. Two flags:

```
share_active > 0.6                      -> "{share}% of the edge over {bench} came from {yr}"
sum(log(1+a) for years != best) <= 0     -> "Edge over {bench} is fully explained by {yr}; the other years net to <= 0"
```

The second condition is the one the panel trips (156%).

### 3.2 Regime split (`regime_split`, L143–154; flag L172–176; `xsect.robustness` L151–154)

Two problems:

(a) **Raw return.** A long-only strategy "wins in up, loses in down" by construction; the flag at
L174–176 ("edge only shows in one regime") is therefore uninformative for the whole
long-only strategy family, and `xsect.py`'s variant ("loses in the worst regime") fires on any
long-only book in a year with a drawdown. Versus its benchmark the picture is different and more
useful:

| SPY regime | Momentum raw | EW raw | **Momentum − EW** | bars |
|---|---:|---:|---:|---:|
| up | +453% | +412% | +8.2% | 1172 |
| down | −4.7% | −17.1% | **+15.1%** | 331 |
| chop | −22.4% | −9.3% | **−14.5%** | 236 |

The thesis's "bull-market vehicle" reading is backwards relative to the honest bar: momentum's
*best* relative regime is *down* markets and its only relative failure is *chop*. That is a
different (and more textbook) story about what the strategy is, and no one could see it because
the number reported was raw.

(b) **Contemporaneous tag.** L146 `trend = spy.pct_change(lookback)` labels bar *t* using SPY's
return *including bar t*. Bars are therefore sorted into "up" partly by their own return. With
`lookback = 60` the contamination is 1/60 per bar — small, but it is a lookahead in a diagnostic
and it biases every "up" cell upward for anything long. Use `trend.shift(1)`.

**Fix.** `regime_split(net, benchmark, bench_net=None, lookback=60, band=0.02)`: tag with
`spy.pct_change(lookback).shift(1)`; when `bench_net` is given, add `'active'` to each regime cell
as `(1+ret_s)/(1+ret_b) − 1`. Flag on the active cells:

```
active < 0 in >= 2 of 3 regimes          -> "Loses to {bench} in {regimes} -- edge is one-regime"
active > 0 in exactly 1 regime           -> "Edge over {bench} shows only in '{r}'"
```

Drop the raw-return version of the flag for long-only strategies (`held.mean() > 0.5` and no
negative positions), or keep it as display.

## 4. `xsect.py`

### 4.1 `robustness()` PSR — WRONG (the known one, still live in three places)

L138 `psr = deflated_sharpe_ratio(monthly.values, n_trials=1, ppy=12)` on `res['net']` — P(true
monthly Sharpe > 0). Every portfolio that owns a rising basket passes:

| Portfolio (30-name core, monthly, net) | Total | Sharpe | PSR |
|---|---:|---:|---:|
| Momentum top-10 | +309% | 0.99 | 0.999 |
| EW universe | +285% | 1.11 | 0.999 |
| Random top-10, seeds 0–4 | +203% … +391% | 0.88–1.24 | **0.996–1.000** |

Dart-throwing scores PSR 1.00. `significance_vs_ew` (P0.1) now sits *beside* this gate, but the
old one is still (i) the source of a red flag at L141 (currently the flag can only fire when the
strategy loses money, so it is harmless but misleading), (ii) written into the verdict record as
`"deflated_sharpe": rob["psr"]` at L398 (the log claims 1.00 for a result with t = 0.34), and (iii)
the number the webapp displays as "probabilistic Sharpe" (`engine_api.py` L360,
`export_track_record.py` L114).

**Fix.** `robustness(res, spy_close, ew_res=None)`: when `ew_res` is given, compute
`psr_active = deflated_sharpe_ratio((monthly(res) − monthly(ew_res)).dropna().values, n_trials=1,
ppy=12)` and (a) flag on `psr_active < 0.95`, (b) return both `psr_raw` and `psr_active`, (c) L398
records `psr_active`. Note `psr_active` and `significance_vs_ew['t']` test the same hypothesis on
the same series (the PSR adds the skew/kurtosis correction); both may be reported, but the gate
must be stated once — keep `t >= 2` as the gate and `psr_active` as its moment-corrected twin.

### 4.2 `significance_vs_ew()` and the verdict block — RIGHT, minor caveats

The series (monthly active, shared window), the statistic (t with ddof = 1), the bootstrap, the
months-won and the leave-one-name-out are all the right questions, and the verdict at L369–381 is
correctly ordered (raw bars → t ≥ 2 → flags). Caveats, none of which changes the 0.34 verdict:

- L188 assumes iid monthly active returns. Momentum active returns are autocorrelated around
  crashes; with n = 83 months this is a second-order effect, but a Newey–West (HAC, lag 3) t-stat
  is a five-line addition and removes the objection. Report both.
- L204 `still_beats = margin_wo > 0` is a point comparison of total returns — the same flaw
  this gate was written to fix. Report the t-stat of the leave-one-out active series instead
  (`t_wo`), and phrase the line as "t = 0.34 → t = {t_wo:.2f} without NVDA".
- The verdict at L375 lets `flags` from §4.1's raw PSR and §3.2's raw regime flag "temper" a
  significant result; once those are computed on active returns this is correct as written.

### 4.3 `sweep()` "k/9 neighbours beat EW" — PARTIALLY RIGHT

L224 `beats_ew = m['total_return'] > ewm['total_return']` — the sign of a total-return margin,
per neighbour. The headline "7/9 beat EW" was read (thesis L95–97, L137) as "the edge is broad".
Per-neighbour monthly-active t-stats on the 30-name core:

| lookback | top-N | margin vs EW | monthly active t | months won |
|---|---:|---:|---:|---:|
| 6mo | 5 | +102% | 0.72 | 51% |
| 6mo | 10 | +31% | 0.36 | 50% |
| 6mo | 15 | −3% | −0.00 | 50% |
| 9mo | 5 | +93% | 0.78 | 56% |
| 9mo | 10 | +49% | 0.56 | 49% |
| 9mo | 15 | −7% | −0.05 | 47% |
| 12mo | 5 | +187% | 1.18 | 52% |
| **12mo** | **10** (canonical) | **+25%** | **0.34** | **48%** |
| 12mo | 15 | +37% | 0.57 | 54% |

Zero of nine neighbours is significant; the best is t = 1.18. "7/9 beat EW" is seven coin flips
that landed heads with margins the size of noise. The sweep is also the only place the panel
engine runs nine specs — if a reader ever picks the +187% one, that is selection, and §2.3's
scan-level discount applies (N = 9).

**Fix.** `sweep()` returns `t_active`, `pct_won` and `n_months` per neighbour (reuse
`_monthly_returns`, shared window as at L219); the headline becomes
`f"{sum(s['t_active'] >= 2 for s in sw)}/{len(sw)} neighbours significant (t >= 2); best t = ..."`.
`beats_ew` stays as a display column.

## 5. `engine_api.run_momentum` and `export_track_record.thesis_001_summary` — WRONG

- `engine_api.py` L345–347 recompute `beats_ew/rand/spy` as point comparisons and L369 returns

- `export_track_record.py` L98–101 builds the status string with the literal prefix

## 7. `walkforward.py` — RIGHT

Checked for the two failure modes that matter:

- **Boundary.** L19–23: train = `idx[:fold*k]`, test = `idx[fold*k : fold*(k+1)]`; disjoint,
  test strictly after train, expanding window. `sanity_check` #5 re-derives this. Positions are
  precomputed on the full series (L13–16) but every strategy in `strategies.py` uses causal
  rolling windows and the engine applies `shift(1)`, so precomputation leaks nothing. No
  lookahead found.
- **Selection metric.** L28 selects on raw in-sample Sharpe. In a rising market that favours
  configs that are long more often, so the OOS series inherits beta. This is *not* a flaw in
  walk-forward: it is honestly reporting what the rule would have done. It becomes a flaw only
  when a downstream gate reads the OOS raw return as skill — which is §1/§2. Do not change
  `select`; it is part of the strategy definition and switching it to an active Sharpe would be a
  new (searched) strategy.
- Minor: the last `len(idx) mod (n_folds+1)` bars (< 6 here) are never in any test fold. Not
  material.

One consequence for §2.3 worth restating: because the OOS series is selection-free with respect
to the grid, the appropriate best-of-N discount *on that series* for the grid is N = 1. The grid
size should be printed (plan/11) but the discount that matters is the number of OOS results a
human reads.

## 8. `metrics.py` — RIGHT (it is not a gate), one enabling addition

`compute_metrics` computes raw Sharpe (L18, vs zero — correct as a *metric*), drawdown, trades,
and is slice-safe as the invariant requires. It is not wrong. It is *missing* the metric every
gate needed, which is why five different callers each improvised `ret > bench_ret`.

**Fix (enabler, not a gate).** Add, without touching `compute_metrics`:

```python
def active_metrics(df, bench_df, ppy=252):
    """Benchmark-relative metrics on the shared index. Returns
    {'active_return': prod(1+a)-1, 'tracking_error': a.std(ddof=1)*sqrt(ppy),
     'information_ratio': a.mean()*ppy / tracking_error,
     't_stat': a.mean() / (a.std(ddof=1)/sqrt(n)),
     'beta': cov(r_s, r_b)/var(r_b), 'alpha_ann': (mean(r_s) - beta*mean(r_b))*ppy,

```

`beta` is the direct answer to "is this beta exposure?": a scan row with β ≈ 0.8 and
`alpha_ann ≈ 0` is the META/tsmom case in one line.
